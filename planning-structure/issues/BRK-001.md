## Objective

Make the repository's build and run contract accurate enough that a future
session can begin and end from a known state.

## Value / context

The current repository contains an SDL tutorial scaffold, uncommitted changes,
and a CMake configuration that does not fully match the roadmap. A durable
project needs one obvious way to configure, build, launch, and diagnose failure.

## In scope

- Decide and record the C++ language level and supported local toolchain.
- Decide which build entry point is canonical.
- Align the documented application dimensions and current build requirements.
- Confirm that a clean configure/build can find the required SDL dependency set
  currently used by the scaffold.
- State the exact launch assumptions in the planning/progress documentation.

## Out of scope

- Implementing gameplay or resource-ownership changes.
- Adding new third-party libraries.
- Creating a GitHub Project or remote issue.

## Requirements

- A new checkout or clean build directory has a documented, repeatable build
  path.
- Build failures identify the missing tool or dependency instead of being
  silently ignored.
- The chosen language/toolchain decision is recorded in the decision ledger.
- The baseline description does not claim that later phases are complete.

## Acceptance criteria

- The canonical configure and build commands succeed from the repository root.
- The resulting executable can be launched using the documented command.
- The chosen C++ standard, compiler assumption, and canonical build entry point
  are no longer ambiguous.
- A reviewer can distinguish the current scaffold from the first real gameplay
  slice by reading the project notes.

## Verification

- Configure and build from a clean build directory.
- Launch the executable and record whether it opens and remains responsive.
- Repeat the build using only the documented command, without relying on an
  unrecorded IDE setting.

## Dependencies

None.

## Risks and decisions

The current working tree is modified. If its intended baseline cannot be
identified, stop and record that ambiguity rather than overwriting or resetting
it. Resolve the C++ standard, canonical build entry point, and toolchain policy
in `decision-ledger.md`.

## Stop conditions / escalation

Stop if the build requires an undocumented machine-specific path, if dependency
discovery is unavailable, or if the desired baseline would require destructive
changes to existing work.
