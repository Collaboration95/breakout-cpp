## Objective

Define the application's screen transition boundary so individual screens can
return a next state without recursively calling one another.

## Value / context

The original project already fixed a recursive state-machine problem. The C++
rewrite should preserve the iterative control-flow improvement while making
state values and transition ownership easier to reason about.

## In scope

- Named screen states for the current core flow.
- One top-level dispatch boundary.
- Return/transition behavior between screen handlers.
- Previous-screen information where the documented back behavior needs it.
- Consistent event and render lifetime for a screen.

## Out of scope

- Implementing every screen.
- Save, score, audio, or settings logic.
- A forced choice between callbacks and polymorphic screen objects.

## Requirements

- Screen handlers do not recursively invoke other screen handlers.
- A transition is represented explicitly rather than inferred from a label.
- The active screen can be replaced without leaving stale screen-local resources.
- The application can terminate through a terminal state or equivalent explicit
  outcome.

## Acceptance criteria

- A small two- or three-state test flow can transition repeatedly without stack
  growth or duplicated event loops.
- The next state and previous-state behavior are inspectable during debugging.
- The dispatcher remains compatible with the continuous runtime loop.

## Verification

- Navigate through a small test sequence several times.
- Exercise a back transition and the terminal quit transition.
- Confirm no handler calls another handler recursively.

## Dependencies

BRK-016.

## Risks and decisions

Do not choose an elaborate screen hierarchy solely because the roadmap mentions
polymorphism. The learner owns that design decision; the requirement is the
observable iterative state behavior.

## Stop conditions / escalation

Stop if the dispatcher needs save/audio/high-score behavior before the core
states can transition.
