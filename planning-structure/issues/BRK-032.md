## Objective

Create the final manual regression path and evidence that the complete rewrite
can be built, launched, played, persisted, and exited repeatedly.

## Value / context

With limited weekly time, a short repeatable checklist is more useful than
remembering whether a feature worked months ago. This is the handoff artifact
for future maintenance and optional backend experiments.

## In scope

- Clean build and launch.
- Main menu, quick game, paddle/ball/bricks, score, and game-over.
- Save/load and reset flows.
- High scores and name input.
- Audio/settings/auto-play.
- Normal close, Escape, and representative failure cases.
- Recording environment, commands, and known limitations.

## Out of scope

- New features discovered during testing.
- A backend migration.
- Rewriting the entire test suite solely for coverage metrics.

## Requirements

- The regression path is ordered by user-visible workflow.
- Each step has an observable expected result.
- A failure identifies the relevant issue/area instead of being a vague “game
  broken” note.
- The clean-run instructions do not depend on unrecorded local state.

## Acceptance criteria

- A fresh build can complete the checklist or produce a bounded list of known
  failures.
- Save, score, settings, and asset data can be reset for another run.
- The final record links failures to the fidelity ledger or a follow-up issue.
- Another agent can use the checklist without asking what “working” means.

## Verification

- Execute the full checklist from a clean build directory.
- Repeat the persistence portions after relaunch.
- Record platform/toolchain details and any intentional deviations.

## Dependencies

BRK-030 and BRK-031.

## Risks and decisions

Do not expand the release scope while writing the regression pass. New ideas
belong in a later backlog, not in the completion gate.

## Stop conditions / escalation

Stop if the application cannot be reset to a known data state or if the
regression sequence exposes a requirement not represented by any issue.
