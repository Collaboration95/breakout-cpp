## Objective

Audit initialization, runtime failure, persistence, and shutdown paths for
resource leaks, invalid ownership, silent corruption, and unhelpful failure
behavior.

## Value / context

The rewrite's main C++ learning value includes RAII and value semantics. A game
that works only on the happy path would not demonstrate that those boundaries
are sound.

## In scope

- SDL, image, font, audio, and text temporary resources.
- Partial initialization failures.
- Missing/malformed save, score, settings, and asset files.
- State-copy and slot-isolation behavior.
- Error messages and exit behavior.

## Out of scope

- New gameplay features.
- Performance optimization unrelated to lifetime or failure handling.
- Replacing libraries.

## Requirements

- Every native resource family has a documented owner and release path.
- Failure paths do not leave stale files, leaked handles, or silently selected
  alternate game state.
- Mutable copies of game, slot, and score data do not alias unexpectedly.
- The chosen failure policy is consistent enough to explain to a user.

## Acceptance criteria

- A reviewer can trace normal and partial-failure ownership for each resource
  family.
- Focused malformed-data and copy-isolation checks pass.
- At least one practical leak/resource diagnostic has been run where available.
- Any known limitation is recorded rather than hidden.

## Verification

- Exercise representative missing-resource and malformed-file cases.
- Run the application through normal shutdown and repeated relaunch.
- Run available sanitizers or platform diagnostics.

## Dependencies

BRK-003, BRK-020, and BRK-026.

## Risks and decisions

Do not treat a clean happy-path run as evidence of complete ownership safety.
Keep the audit proportional to the local toolchain and document unavailable
diagnostics.

## Stop conditions / escalation

Stop if a resource's owner cannot be identified or if fixing the issue would
change a product decision not recorded in the ledger.
