## Objective

Load the carried-over visual assets through an explicit path policy and render
the original background panel as the base of the active frame.

## Value / context

The assets are already present, but the current scaffold mixes tutorial paths and
does not establish whether the working directory or executable location is the
source of truth. A stable asset boundary prevents every later screen from
inventing its own path logic.

## In scope

- Asset-root policy for the copied PNG assets.
- Background-panel loading and ownership.
- Background draw order relative to game geometry.
- Observable handling of a missing or incompatible asset.

## Out of scope

- Font or music loading.
- Button behavior.
- Save-file paths or data files.
- Visual redesign of the original background.

## Requirements

- The background panel is drawn as the base layer of the active frame.
- The chosen asset-root policy is recorded in the decision ledger.
- Asset loading does not leak partially acquired resources.
- Missing assets produce a diagnosable result rather than an unexplained blank
  application.

## Acceptance criteria

- The manual run shows the copied background panel behind existing geometry.
- The application can be launched using the documented asset-path assumption.
- A missing-asset scenario is reported and cleaned up safely.
- Existing gameplay geometry remains visible above the background.

## Verification

- Run from the documented launch directory and inspect the visual layering.
- Test a deliberately unavailable asset path without leaving the process broken.
- Confirm the asset file used is the copied `background-panel.png`.

## Dependencies

BRK-003.

## Risks and decisions

Resolve the asset-root decision before marking Ready. Do not solve path
portability by scattering absolute paths through feature code.

## Stop conditions / escalation

Stop if the asset strategy requires a packaging or installer design that is not
needed for the local learning project.
