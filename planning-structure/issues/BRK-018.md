## Objective

Connect the main menu, quick game, game, quit confirmation, back, and game-over
routes into a usable core application flow.

## Value / context

This is the point where the playable core becomes an application rather than a
single test scene. It also establishes transition seams for save/load, scores,
audio, and settings.

## In scope

- Main menu choices documented by the reference.
- Quick-game entry into a fresh round.
- Quit confirmation and return-to-previous-screen behavior.
- Game-over routes back to the main menu or later score screen placeholder.
- Documented per-screen titles and background treatment where already available.

## Out of scope

- Complete save/load, high-score, audio, or settings behavior.
- Recreating every menu screen in one issue.
- New navigation features not present in the reference.

## Requirements

- Every core route has an explicit transition and a visible response.
- “Go Back” returns to the correct prior screen for the supported flow.
- Quick Game starts a clean round without stale score or brick state.
- Quit confirmation can be cancelled or completed without recursive screen calls.

## Acceptance criteria

- A manual user can navigate main menu → quick game → game → quit → back.
- A manual user can navigate game → game-over → main menu.
- Window close/Escape behavior remains consistent with the screen state.
- Display labels can change without changing route semantics.

## Verification

- Exercise every listed route at least twice.
- Test quit from the game and from a menu.
- Start two quick games and confirm round state is reset.

## Dependencies

BRK-017 and BRK-015.

## Risks and decisions

Use placeholders for screens owned by later sprints rather than expanding this
issue. Preserve the original route semantics unless the decision ledger says
otherwise.

## Stop conditions / escalation

Stop if save or score behavior becomes necessary to navigate the core flow.
Create or unblock the relevant later issue instead of coupling unrelated work.
