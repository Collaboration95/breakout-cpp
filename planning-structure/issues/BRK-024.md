## Objective

Persist the validated top-three score table and safely reject malformed or
incompatible records when loading it.

## Value / context

The original shipped score rows can contain hashes from an older scheme. The
rewrite must make the compatibility boundary explicit rather than displaying
unverified or silently corrupted scores.

## In scope

- High-score file location under the chosen path policy.
- Writing the retained entries.
- Loading up to the supported number of entries.
- Integrity verification on load.
- Missing, malformed, and incompatible row behavior.
- Round-trip checks for valid entries.

## Out of scope

- Game-over insertion rules.
- The high-score screen layout.
- A migration tool for legacy hash formats unless separately approved.

## Requirements

- Only entries that pass the chosen integrity rule enter the active table.
- A malformed or invalid row cannot displace valid rows without an explicit
  policy.
- Missing score data has a defined empty-table outcome.
- The file format and legacy-hash policy are documented.

## Acceptance criteria

- Valid entries survive a write/read round trip.
- An edited score, name, timestamp, or hash is rejected according to policy.
- The shipped incompatible hash shape is not treated as valid by accident.
- A malformed row does not crash the application or corrupt unrelated entries.

## Verification

- Run focused persistence checks with valid, invalid, partial, and missing files.
- Relaunch after writing a table and inspect ordering and validation results.
- Record the behavior of a legacy 64-character hash row if encountered.

## Dependencies

BRK-023.

## Risks and decisions

Keep the high-score file separate from save slots. Resolve whether invalid rows
are skipped, reset, or cause a visible warning before marking this issue Ready.

## Stop conditions / escalation

Stop if compatibility requires importing a different cryptographic dependency or
if the chosen error policy would discard valid neighboring rows.
