## Objective

Give the SDL subsystems and currently used native handles a clear ownership
boundary so normal exit and partial initialization are both safe.

## Value / context

The rewrite is meant to teach C++ ownership rather than reproduce a manually
managed global context. This is the first place where cleanup behavior should be
made reliable before more resources and systems are added.

## In scope

- SDL initialization and shutdown.
- Window and renderer ownership.
- Any image/media handle already required by the current scaffold.
- Correct cleanup when a later initialization step fails.
- Preventing accidental copying of owning state.

## Out of scope

- Font, music, save-file, or gameplay ownership.
- A final `Application` decomposition.
- Adding caches or abstractions that are not required to establish lifetime.

## Requirements

- Each acquired native resource has one clear owner and one release path.
- Cleanup occurs in a valid dependency order.
- Initialization failure does not leak resources acquired before the failure.
- Normal process exit does not rely on a special manually remembered cleanup
  call being made from every branch.

## Acceptance criteria

- A normal close releases all resources used by the foundation.
- A deliberately triggered initialization failure releases earlier resources.
- Ownership boundaries are understandable without tracing a global variable
  through the whole program.
- The application still passes BRK-002's responsiveness and exit checks.

## Verification

- Run the application normally.
- Exercise at least one failure path, such as an unavailable resource or
  initialization step, without leaving a running process behind.
- Use the available platform leak/resource diagnostics if practical.

## Dependencies

BRK-002.

## Risks and decisions

Keep this issue limited to lifetime. Do not redesign the game model or choose
the final screen architecture here. The choice of exception, error result, or
another failure-reporting approach remains the learner's decision unless it
violates the acceptance criteria.

## Stop conditions / escalation

Stop if a cleanup path would require broad changes to unrelated gameplay code or
if native handles have unclear ownership. Record the ownership conflict instead
of hiding it with additional global state.
