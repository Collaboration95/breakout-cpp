## Objective

Make the paddle visible and controllable using left/right controls,
including faster movement while Left Alt is held, while keeping it
within window bounds (any visible range).

## Value / context

This is the first player-facing interaction and establishes the relationship
between input, mutable game state, and rendering.

## In scope

- Paddle exists (any reasonable size/location, visible).
- Left/right movement.
- Left Alt faster movement (any faster amount, just needs to exist).
- Horizontal boundary behavior (any clamping that keeps paddle visible).
- Input held over multiple frames.

## Out of scope

- Ball movement or paddle collision.
- Auto-play.
- Menus or name entry.

## Requirements

- The paddle exists and starts in a visible location (any position).
- Left and right controls move it in the expected directions.
- Left Alt moves faster than normal (any faster amount, just needs to exist).
- Movement cannot take the paddle outside the window (any bounds that keep it visible).

## Acceptance criteria

- A manual run can move the paddle from near one allowed limit to the other.
- Holding Left Alt produces faster movement than normal (any faster amount).
- Repeated input cannot push the paddle beyond either boundary.
- The paddle remains visible and responsive while the window is active.

## Verification

- Test left, right, and both boundary conditions.
- Test normal and accelerated movement separately.
- Confirm the foundation exit behavior still works while input is being held.

## Dependencies

BRK-004.

## Risks and decisions

Faster Alt movement just needs to exist (any faster amount); exact 2× not required.

## Stop conditions / escalation

Stop if input handling requires a screen-state system or if boundary behavior
cannot be defined from the documented geometry. Do not add menu abstractions to
solve this issue.
