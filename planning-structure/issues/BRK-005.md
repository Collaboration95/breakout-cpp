## Objective

Make the paddle visible and controllable using the original left/right controls,
including the documented accelerated movement, while keeping it in the intended
horizontal range.

## Value / context

This is the first player-facing interaction and establishes the relationship
between input, mutable game state, and rendering.

## In scope

- The documented paddle dimensions and starting location.
- Left/right movement.
- Left Alt accelerated movement.
- Horizontal boundary behavior using the documented padding.
- Input held over multiple frames.

## Out of scope

- Ball movement or paddle collision.
- Auto-play.
- Menus or name entry.

## Requirements

- The paddle starts centered at the documented position.
- Left and right controls move it in the expected directions.
- Left Alt changes movement speed as specified by the reference behavior.
- Movement cannot take the paddle outside the documented playable range.

## Acceptance criteria

- A manual run can move the paddle from near one allowed limit to the other.
- Holding the accelerated control produces the intended faster movement.
- Repeated input cannot push the paddle beyond either boundary.
- The paddle remains visible and responsive while the window is active.

## Verification

- Test left, right, and both boundary conditions.
- Test normal and accelerated movement separately.
- Confirm the foundation exit behavior still works while input is being held.

## Dependencies

BRK-004.

## Risks and decisions

The original's Alt behavior is a known quirk/feature. Preserve its visible speed
unless the decision ledger explicitly changes it.

## Stop conditions / escalation

Stop if input handling requires a screen-state system or if boundary behavior
cannot be defined from the documented geometry. Do not add menu abstractions to
solve this issue.
