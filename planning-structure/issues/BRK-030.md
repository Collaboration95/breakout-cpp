## Objective

Review every documented quirk or bug touched by the rewrite and record whether
the C++ version reproduces it, fixes it, or intentionally leaves it outside
scope.

## Value / context

Without a final ledger, differences discovered during play can look like
accidental bugs or failed ports. This issue turns fidelity into an explicit
learning artifact.

## In scope

- The quirks and bugs in `docs/01-c-game-reference.md`.
- Decisions recorded while implementing physics, input, screens, persistence,
  scores, audio, and settings.
- Evidence or rationale for each relevant choice.
- Identification of any unimplemented behavior.

## Out of scope

- Adding new features.
- Rewriting code solely to eliminate harmless stylistic differences.
- Optional backend migration.

## Requirements

- Each relevant behavior has a status: reproduced, fixed, deferred, or not
  applicable.
- Behavior-changing fixes have a short rationale.
- Deferred decisions identify a concrete follow-up or release limitation.
- The ledger distinguishes player-visible compatibility from internal C quirks.

## Acceptance criteria

- Another agent can explain the intentional differences without reading the
  entire source history.
- No known decision is silently left in “whatever the implementation did.”
- The project proposal's fidelity claim matches the ledger.

## Verification

- Walk the quirk catalogue and cross-reference issue evidence.
- Manually reproduce the player-visible choices that matter.
- Ask the auditor to identify any undocumented divergence.

## Dependencies

BRK-012, BRK-015, BRK-018, BRK-025, and BRK-029.

## Risks and decisions

This is a decision and evidence task, not a license to expand scope. If a choice
cannot be made confidently, mark it deferred rather than inventing certainty.

## Stop conditions / escalation

Stop if the reference docs contradict one another or if a behavior cannot be
observed without the original C project. Record the missing evidence.
