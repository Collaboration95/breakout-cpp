## Objective

Build the in-memory top-three score behavior and its integrity calculation as a
copyable, SDL-independent domain boundary.

## Value / context

The original score module is the clearest pure-logic seam. Rebuilding it
separately gives the learner a focused opportunity to use value semantics and
typed sorting before adding file and screen concerns.

## In scope

- Score entry values: name, score, timestamp, and integrity value.
- DJB2-compatible hashing if compatibility is retained.
- Integrity verification.
- Descending top-three ordering and replacement behavior.
- Handling empty entries and equal-score ordering policy.

## Out of scope

- Reading/writing the high-score file.
- Game-over screen behavior.
- SDL or text rendering.

## Requirements

- An entry's integrity value is derived from the chosen fields consistently.
- Invalid integrity data is distinguishable from valid data.
- Adding a score produces at most three retained entries in the chosen order.
- Entries can be copied and sorted without manual string ownership.
- The compatibility decision for the C/DJB2 behavior is recorded.

## Acceptance criteria

- Focused checks cover hash creation, valid verification, invalid verification,
  insertion, sorting, truncation, and empty-table behavior.
- Equal-score behavior is deterministic and documented.
- The logic has no SDL dependency.

## Verification

- Run the focused score checks.
- Compare known DJB2-compatible examples if compatibility is selected.
- Mutate each integrity-relevant field and confirm invalidation.

## Dependencies

BRK-019.

## Risks and decisions

Do not use `std::hash` as a silent replacement if the goal is file compatibility.
If a different integrity rule is chosen, record that existing legacy rows are no
longer expected to load.

## Stop conditions / escalation

Stop if timestamp representation or equal-score ordering is unclear enough to
make persistence non-deterministic.
