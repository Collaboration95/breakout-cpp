## Objective

Create reusable clickable UI behavior whose action is represented as data or
behavior separate from the human-readable label.

## Value / context

The C version allocates buttons manually and dispatches by comparing display
text. The rewrite should teach value semantics and prevent a label change from
silently changing navigation behavior.

## In scope

- Button geometry and label presentation.
- Hit testing for pointer input.
- A way to associate a button with an action or callback without parsing its
  label.
- Collection and lifetime behavior for a screen's buttons.

## Out of scope

- The screen state machine.
- Save-slot-specific rendering.
- Keyboard navigation or accessibility beyond the existing mouse interaction.

## Requirements

- A button can be rendered and hit-tested using the documented rectangle.
- Display text is not the authoritative source of the action.
- Buttons have no manual string ownership hazard.
- The behavior is reusable by more than one screen.

## Acceptance criteria

- A test screen can render at least two buttons with distinct actions.
- Clicking inside and outside their rectangles produces the expected distinction.
- Changing a label in a development test does not change the associated action.
- Repeated screen construction/destruction does not leak button-owned resources.

## Verification

- Exercise edge and interior points for hit testing.
- Render two buttons with intentionally unrelated labels and actions.
- Re-enter the test screen repeatedly.

## Dependencies

BRK-014.

## Risks and decisions

Choose the simplest behavior model that supports later screens. Record the
choice only if it materially affects the learning objective or creates a broad
ownership commitment.

## Stop conditions / escalation

Stop if the issue starts implementing navigation or if button behavior requires
parsing labels or slot numbers from display strings.
