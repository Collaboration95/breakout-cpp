## Objective

Establish a simulation cadence whose movement is based on elapsed time rather
than on how quickly the main loop happens to spin.

## Value / context

The C version updates gameplay once per loop while throttling only rendering.
That makes the game speed machine-dependent. Correct timing is both a quality
fix and a focused C++/SDL lesson.

## In scope

- Measuring elapsed time consistently.
- Advancing simulation in a stable cadence.
- Rendering the latest state without making rendering frequency define physics.
- Handling a delayed or unusually long frame without runaway work.

## Out of scope

- Wall, paddle, or brick collision rules.
- Audio timing.
- A generalized engine scheduler.

## Requirements

- The same elapsed play time produces approximately the same ball movement on
  repeated runs with different render load.
- The loop remains responsive during normal event processing.
- The timing policy for unusually long frames is deliberate and recorded if it
  affects behavior.

## Acceptance criteria

- The ball can move under the new cadence without visibly changing speed merely
  because the render loop is allowed to run faster.
- The timing approach is explainable in terms of simulation time and render
  time.
- No collision behavior is being hidden inside this timing issue.

## Verification

- Run the same short movement test under normal and intentionally heavier render
  conditions.
- Compare elapsed-time movement rather than raw loop iterations.
- Record any chosen catch-up or frame-clamp policy.

## Dependencies

BRK-005 and BRK-006.

## Risks and decisions

Resolve the physics representation question in the decision ledger if integer
positioning becomes a visible limitation. Do not compensate for timing by
changing gameplay speed constants without recording why.

## Stop conditions / escalation

Stop if the issue begins requiring collision-specific exceptions or if the loop
cannot distinguish simulation updates from presentation.
